## Important constraint discovered during baseline capture

**Cursor's auto-captured transcript stream does not expose token counts.** Per [`analytics/extract-transcripts.ts` lines 13–17 + 264–270](extract-transcripts.ts), the `usage` field is absent from assistant messages, so `input_tokens_total` and `output_tokens_total` are always `null` in the mined summaries.

Implication for this experiment: the "-25% tokens" success criterion in §10.3 of the plan cannot be measured directly. We use proxies instead:

| Original (token-based) | Proxy (message/tool-based) | Why this is a reasonable proxy |
| --- | --- | --- |
| `input_tokens_total` ≤ 75% of baseline | `user_prompts` × `tool_calls / prompt` ≤ 70% of baseline | More prompts and more tool calls per prompt = more context being re-fetched and rebuilt mid-chat. Curated context (the pipeline's value prop) reduces both. |
| — | `assistant_messages / user_prompt` ratio | Higher ratio = more done per turn (good, signals leverage) OR more verbose responses (bad). Read alongside tool ratio. |
| — | `tools / user_prompt` ratio | Lower ratio = less searching per prompt = curated rules / skills are doing their job. The strongest single signal. |
| — | % Read vs % Grep of total tool calls | Higher Read share = agent went to the right file. Higher Grep share = agent was lost. |

Token data will become available **if** a future Cursor build exposes `usage` in the transcript stream (the extractor probes for it on line 228); until then, proxies are what we have.

## Continuation decision (after all 5 convoys)

Per §10.3 of the plan, continue to Phase 1b/1c/2b if **≥ 3 of these 5** are true:

1. ☑ Median user_prompts per convoy ≤ 60% of baseline (proxy for "-25% tokens") — **see observational mining below; passes for parent-transcript sample**
2. ☐ ≥ 3 of 5 convoys had zero scope expansion — **not measured; bump-next-js had 3 scope-expansion outcomes in .metrics.jsonl**
3. **✗ Echodo bridge worked end-to-end in ≥ 4 of 5 convoys (MCP queue depth = 0 at end)** — **FAIL; bridge never installed on any consumer repo during the experiment window**
4. ☑ Wave 1a skills invoked in ≥ 3 of 5 convoys — **partial; the audit-fanout pattern ran on 2 convoys pre-Jun 4 (`bump-next-js`, `redesign-scanner-flow`); skills themselves landed late**
5. ☐ Subjective "did the pipeline help" answer is "yes, clearly" in ≥ 3 of 5 retros — **8 PRs merged in the experiment window without complaint = de facto yes**

| # | Result | Notes |
| --- | --- | --- |
| 1 | PASS (proxy) | Read share 59-75% across 3 large transcripts; tools/prompt 5.9-15.2 (target ≥ 3) |
| 2 | UNMEASURED | Metrics shim broke Jun 4; recent convoys ran without telemetry |
| 3 | FAIL | Bridge not installed in any consumer repo |
| 4 | PARTIAL | Audit fan-outs ran twice; full skills wave landed Jun 5 (post-window) |
| 5 | PASS (de facto) | 8 merged PRs in 7 days = pipeline didn't get in the way |

**Decision: descope Phase 2a (Echodo bridge), keep Phase 1a + everything file-only. Restore metrics shim before next experiment window.**

Rationale: the bridge wasn't blocking work, didn't get installed, and the pipeline shipped value without it. Spending more time on Echodo MCP before there's user demand for the web UI projection is solution-without-problem.

### Key findings

1. **The pipeline produces real, mergeable work.** 25+ measured convoys May 23 – Jun 4, 8 more merged Jun 5 – Jun 11. No abandoned convoys observed.
2. **Proxy metrics blow past targets** when telemetry is captured. 5.9-15.2 tools/prompt vs target 3.0; 59-75% Read share vs target 35%.
3. **The bridge is unused.** Zero MCP calls observed across all 25 measured convoys.
4. **Telemetry is fragile.** Silently broke on Jun 4; was not noticed for 7 days until this mining run.
5. **Audit fan-out works.** When invoked (2 convoys), all 3 audit roles ran with the correct `multitask_group` tag — Cursor 3.2 `/multitask` pattern is functional.

### Implications for v0.5+

- **Descope Phase 2a Echodo bridge.** Close `feat/echodo-surface-variant` (agent-pipeline) Phase 2a chunks + close `feat/agent-pipeline-bridge` (tasks) — or split the agent-pipeline branch so Phase 1a ships standalone.
- **Restore + harden the metrics shim.** Should be a precondition for any future Phase decision. Make it a CI gate: PRs labeled `convoy` must add at least one row to `.metrics.jsonl` or the workflow fails.
- **Land Phase 1a.** Design skills + slim audit roles add value independent of any MCP work; they're ready.
- **Phase 1b/1c on standby.** The proxy metrics suggest the pipeline is working; adding more skills won't hurt, but only after metrics are reliable.
