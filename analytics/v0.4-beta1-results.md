## Important constraint discovered during baseline capture

**Cursor's auto-captured transcript stream does not expose token counts.** Per [`analytics/extract-transcripts.ts` lines 13–17 + 264–270](extract-transcripts.ts), the `usage` field is absent from assistant messages, so `input_tokens_total` and `output_tokens_total` are always `null` in the mined summaries.

Implication for this experiment: the "-25% tokens" success criterion in §10.3 of the plan cannot be measured directly. We use proxies instead:

| Original (token-based) | Proxy (message/tool-based) | Why this is a reasonable proxy |
| --- | --- | --- |
| `input_tokens_total` ≤ 75% of baseline | `user_prompts` × `tool_calls / prompt` ≤ 70% of baseline | More prompts and more tool calls per prompt = more context being re-fetched and rebuilt mid-chat. Curated context (the pipeline's value prop) reduces both. |
| — | `assistant_messages / user_prompt` ratio | Higher ratio = more done per turn (good, signals leverage) OR more verbose responses (bad). Read alongside tool ratio. |
| — | `tools / user_prompt` ratio | Lower ratio = less searching per prompt = curated rules / skills are doing their job. The strongest single signal. |
| — | % Read vs % Grep of total tool calls | Higher Read share = agent went to the right file. Higher Grep share = agent was lost. |

Token data will become available **if** a future Cursor build exposes `usage` in the transcript stream (the extractor probes for it on line 228); until then, proxies are what we have.
