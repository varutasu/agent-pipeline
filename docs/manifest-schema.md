# Manifest schema — `.agent-context-manifest.yml`

The manifest is a single YAML file each bootstrapped repo carries at its root. It is the contract between the pipeline (the producer) and the bootstrapped repo (the consumer). The `bootstrap-agent-context` skill writes it at install time; the `sync-agent-context` skill reads, diffs, and rewrites it on update.

## Why a manifest

Without a manifest, the only way to know whether a repo is on the latest agent-pipeline templates is to diff every artifact by hand. With a manifest:

- A single read tells you which version of the pipeline the repo is on.
- A single hash comparison per artifact tells you whether the user customized it.
- Updates can be applied **selectively** instead of all-or-nothing.

Cost: one extra file per repo (~30-50 lines of YAML). Benefit: every future update becomes a tractable, reviewable diff.

## File location

`<repo-root>/.agent-context-manifest.yml` — always at the repo root, never nested.

Not gitignored. The manifest IS the source of truth for "what version is this repo on"; commit it.

## Top-level fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `schema_version` | integer | yes | This document defines `schema_version: 1`. Breaking changes bump it. |
| `pipeline_version` | string | yes | Pipeline version that last touched this manifest (matches `version.txt`). E.g. `"0.3.0"` or `"0.1.3-trimble"`. |
| `pipeline_source` | string | yes | Canonical pipeline URL. `https://github.com/varutasu/agent-pipeline` for upstream; fork URL for forks. |
| `installed_at` | ISO 8601 | yes | When the bootstrap skill first wrote this manifest. Never changes after that. |
| `last_synced_at` | ISO 8601 | yes | When the sync skill last reconciled this manifest. Updated by `sync-agent-context`. |
| `layers` | string[] | yes | Subset of `["L0", "L1", "L2", "L3"]` — which layers were installed. |
| `artifacts` | object[] | yes | One entry per installed file. See below. |

## `artifacts[]` entries

Each artifact is one file written into the consumer repo by the bootstrap skill.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `path` | string | yes | Where the file lives in the consumer repo, relative to repo root. E.g. `.cursor/agents/role-conductor.md`. |
| `source` | string | yes | The template path within the pipeline repo, relative to its root. E.g. `skills/bootstrap-agent-context/templates/L2-roles/role-conductor.md`. |
| `version` | string | yes | Pipeline version when this artifact was last installed or updated. Matches `pipeline_version` after a fresh install; may lag after a partial sync. |
| `installed_hash` | string | yes | `sha256:<hex>` of the file as the bootstrap or sync skill wrote it. Used to detect local modifications. |

## Drift classification

The sync skill compares three values per artifact:

1. **Manifest `version`** — version recorded at last install/sync
2. **Pipeline source file hash** — current hash in the pipeline repo
3. **Consumer file hash** — current hash of the installed file in the consumer repo

Resulting state matrix:

| Local matches `installed_hash`? | Pipeline source changed since `version`? | State | Recommended action |
| --- | --- | --- | --- |
| yes | no | `up-to-date` | no-op |
| yes | yes | `behind` | offer to update; safe overwrite |
| no | no | `customized` | leave alone; user owns this file |
| no | yes | `conflict` | show 3-way diff; require user choice |

`up-to-date` and `customized` need no user input. `behind` and `conflict` get presented for per-file review.

## Worked example

```yaml
schema_version: 1
pipeline_version: "0.3.0"
pipeline_source: "https://github.com/varutasu/agent-pipeline"
installed_at: "2026-05-14T16:30:00Z"
last_synced_at: "2026-05-14T16:30:00Z"
layers: [L1, L2, L3]
artifacts:
  - path: ".cursor/agents/role-conductor.md"
    source: "skills/bootstrap-agent-context/templates/L2-roles/role-conductor.md"
    version: "0.3.0"
    installed_hash: "sha256:7f8e9a1b..."
  - path: ".cursor/rules/no-go-zones.mdc"
    source: "skills/bootstrap-agent-context/templates/L1-context/no-go-zones.mdc"
    version: "0.3.0"
    installed_hash: "sha256:3c2d4e5f..."
  - path: ".github/workflows/ci.yml"
    source: "skills/bootstrap-agent-context/templates/L3-pipeline/nextjs-prisma/ci.yml.template"
    version: "0.3.0"
    installed_hash: "sha256:9b8a7c6d..."
```

## Files the manifest does NOT track

The bootstrap skill writes some files the manifest deliberately omits, because they're either user-authored or expected to drift:

- **`AGENTS.md`** — hand-curated per repo. Tracking the install hash gives false drift signals. Skipped.
- **`docs/SCHEMA_MAP.md`** — regenerated by `scripts/generate-schema-map.ts` whenever the schema changes; not a static template.
- **`.convoys/<slug>.md` and brief files** — user content, generated by role-conductor and role-architect at runtime.
- **`.convoys/.metrics.jsonl`** — analytics output, appended by L2 roles.

The script that GENERATES `docs/SCHEMA_MAP.md` (the `generate-schema-map.ts` itself) IS tracked — it's a template the consumer installed once.

## Hash format

`sha256:<lowercase hex>`. Computed with:

```bash
shasum -a 256 <file> | awk '{print "sha256:" $1}'
```

The `sha256:` prefix is mandatory so future schema versions can mix in other algorithms (`blake3:...`, etc.) without ambiguity.

## Schema version bumps

`schema_version: 1` is the current contract. If we need to break it (e.g. add a required field, change hash format), bump to 2 and ship a migration in the sync skill. Until then, treat the schema as stable — consumers depend on it.

## Implementation tooling

There is no separate CLI for the manifest. Two skills own it:

- `bootstrap-agent-context` writes it once at install time, listing every artifact it actually wrote.
- `sync-agent-context` reads it, computes diffs, asks the user per-file, and rewrites it.

Both skills use `shasum` (macOS + Linux) and standard YAML parsing. No npm dependencies.
